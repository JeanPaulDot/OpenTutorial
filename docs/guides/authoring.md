# Authoring

Specs are plain JSON, so they can be written by hand, generated by the recorder,
or edited by someone who does not write front-end code.

## Editor autocomplete

Point `$schema` at the published JSON Schema:

```json
{
  "$schema": "https://unpkg.com/@opentutorial/core/dist/spec.schema.json",
  "specVersion": 1,
  "id": "welcome",
  "title": "Welcome",
  "steps": []
}
```

VS Code, WebStorm and anything else with JSON Schema support will then complete
field names, validate enums, and flag typos as you type.

Prefer a local path in a monorepo:

```bash
npx opentutorial schema     # prints the absolute path to spec.schema.json
```

## The recorder

Point and click at your own app; get JSON out.

```
https://app.example.com/dashboard?ot-record=1
```

The global build enables this automatically. With a bundler:

```ts
import { enableRecorderFromUrl } from '@opentutorial/core/authoring';

if (import.meta.env.DEV) enableRecorderFromUrl();
```

Hover to highlight an element, click to capture it as a step, reorder or remove
steps in the panel, then **Copy JSON**.

Programmatically:

```ts
import { startRecorder } from '@opentutorial/core/authoring';

const recorder = startRecorder({
  tourId: 'billing-setup',
  title: 'Set up billing',
  minScore: 60,                                  // warn below this
  onChange: (spec) => console.log(spec),
  onExport: (spec, json) => save(json),          // default: copy to clipboard
});

recorder.getSpec();
recorder.toJSON();
recorder.stop();
```

The recorder never captures its own UI, and an empty recording still exports a
valid spec with one placeholder step — so the output always opens.

Each captured step shows the selector's stability score and warns when it is
below `minScore`. A warning means: add a `data-tour` attribute to that element.

## Selector scoring

```ts
import { generateSelectors, bestSelector } from '@opentutorial/core/authoring';

bestSelector(document.querySelector('#pay')!);
// { selector: '[data-testid="pay-btn"]', score: 95,
//   reason: 'test hook attribute', fallbacks: ['#pay'], text: 'Pay now' }
```

| Score | Meaning |
|---|---|
| 90+ | A dedicated hook (`data-tour`, `data-testid`, …). Ship it. |
| 70–89 | A stable id or semantic attribute. Fine. |
| 40–69 | Class or structural. Will survive a while. |
| < 40 | Positional path. Expect it to break. |

Generated ids (`radix-1234`, `:r0:`) and CSS-in-JS classes (`css-1a2b3c`,
`sc-AbCdEf`) are rejected outright — they change on every build.

## Debug overlay

```ts
createTutorialLayer({ specs, debug: true });
```

```tsx
<TourProvider specs={specs} debug />
```

A corner panel showing the active spec, the step index, the resolved target,
the live context, and how every `showIf` actually evaluated. It answers the
question "why is this step not showing?" without a debugger.

Log every event to the console:

```ts
import { logEvents } from '@opentutorial/core/authoring';
const stop = logEvents();
```

## CLI

```bash
npx opentutorial <command>
```

| Command | Purpose |
|---|---|
| `validate [paths…]` | Validate spec JSON. Defaults to the current directory. |
| `lint-selectors <url> [paths…]` | Check every step selector against a live page. |
| `preview <url> [paths…]` | Serve a page that runs your specs against a URL. |
| `schema` | Print the path to `spec.schema.json`. |
| `version` | Print the package version. |

| Flag | Applies to | Notes |
|---|---|---|
| `--strict` | `validate` | Treat warnings as failures. |
| `--json` | `validate` | Machine-readable output. |
| `--quiet`, `-q` | `validate` | Only print files with issues. |
| `--networkidle` | `lint-selectors` | Wait for network idle first. |
| `--port <n>` | `preview` | Port for the preview server. Default 4180. |

Exit codes: `0` pass · `1` validation or selector failures · `2` bad usage or a
missing prerequisite.

### Validating in CI

```yaml
- name: Validate tour specs
  run: npx opentutorial validate specs/**/*.json --strict
```

Accepts files, directories and globs, and expands `**` itself — so it behaves
the same in bash, PowerShell and cmd.

It also catches what a per-spec validator cannot: **duplicate tour ids across
files**, which silently shadow each other at runtime.

```
✓ specs/welcome.json
✗ specs/billing.json
  error   $.steps[1].target — required when advanceOn === "target-click"
  warning $.title — longer than 60 chars (got 74)
3 spec(s), 1 error(s), 1 warning(s)
```

### Checking selectors against a live app

```bash
npx opentutorial lint-selectors http://localhost:3000 specs/
```

```
✓ onboarding/intro   [data-tour="dashboard"]
! onboarding/filter  .row (matches 4)
✗ onboarding/invite  #invite-btn no match
2 step(s), 1 unmatched
```

Needs Playwright, which is deliberately not bundled:

```bash
npm i -D playwright && npx playwright install chromium
```

Run it against a staging deploy in CI and you find broken tours before users do.

### Previewing without a rebuild

```bash
npx opentutorial preview http://localhost:3000 specs/
```

Serves a page at `http://127.0.0.1:4180` that frames your app and runs the specs
against it, with a picker for which tour to start. The loop becomes *edit JSON →
refresh* instead of *edit JSON → rebuild → click to the right screen → start*.

The target must be **same-origin** with the preview server for selectors to
resolve — a cross-origin frame cannot be inspected by anyone, and the page says
so when that happens.

## Typed authoring

```ts
import { defineSpec, type SpecStepId } from '@opentutorial/core';

const spec = defineSpec({
  specVersion: 1,
  id: 'welcome',
  title: 'Welcome',
  steps: [
    { id: 'intro', title: 'Hi', content: 'x' },
    { id: 'done', title: 'Bye', content: 'y' },
  ],
});

type StepId = SpecStepId<typeof spec>;   // 'intro' | 'done'
```

`defineSpec` is an identity function that pins literal types, so a typo in a
`next` target or a `goTo` call is a compile error rather than a runtime no-op.

Build variants from a base spec:

```ts
import { extendSpec } from '@opentutorial/core';

const enterprise = extendSpec(base, {
  id: 'welcome-enterprise',
  theme: { accent: '#0f766e' },
});
```

## Publishing the schema

`spec.schema.json` ships in `dist/` and carries an `$id` pointing at the unpkg
URL, so the reference above resolves without configuration.

Submitting it to [SchemaStore](https://www.schemastore.org/) would make
`*.tour.json` files validate with no `$schema` line at all. That needs a pull
request against their catalog — it is on the [roadmap](../../ROADMAP.md) and
not yet done.

## Workflow

1. Add `data-tour` attributes to the elements you intend to target.
2. Record a draft with `?ot-record=1`.
3. Edit the copy in your editor, with `$schema` for autocomplete.
4. Iterate with `npx opentutorial preview`.
5. `npx opentutorial validate --strict` in CI.
6. `npx opentutorial lint-selectors` against staging.
7. Watch `target-not-found` in production.
